1. Tóm tắt điều hành

Khách hàng đến với agent hỗ trợ thường là khi họ gặp vấn đề. Trả lời câu hỏi là phần dễ; phần khó là vẫn phải có người làm việc thật: tra đơn hàng, reset thiết bị, xử lý hoàn tiền, đổi gói. Đề xuất này bổ sung cho Crove-Desk một lớp action tools để AI agent tự hoàn thành việc đó: kết nối API nghiệp vụ thật, thực thi hành động trong giới hạn chính sách, có người duyệt khi rủi ro cao, và ghi vết từng bước.

Điểm quan trọng nhất: Crove-Desk không phải xây từ đầu. Khi rà code thực tế, repo đã có sẵn một bộ khung governance chất lượng cao: PolicyGuard với risk level và giới hạn gọi tool, audit 3 lớp (AgentRun / AgentStep / AgentToolCall), MCP client với allow-list do admin chọn tay. Còn thiếu đúng 3 mảnh:

  • Business API tools - cho doanh nghiệp tự đăng ký endpoint có sẵn thành tool agent gọi được (hiện tool chỉ tồn tại dạng code cứng hoặc MCP server ngoài).
  • Policy-as-code - luật nghiệp vụ (ngưỡng tiền, điều kiện entitlement) chạy bằng engine biểu thức an toàn, quyết định cho phép / từ chối / cần người duyệt.
  • Staff approval gate - khi vượt ngưỡng, hành động dừng vào hàng chờ duyệt cho CS lead, thay vì chỉ hỏi xác nhận khách hàng như hiện tại.

Ước lượng tổng: 9 đến 16 ngày làm việc (solo dev + agent hỗ trợ), chia 4 pha; Pha 0 chỉ tốn 1-2 ngày để ra quyết định go/no-go.

Model đề xuất - Policy phán quyết - Người duyệt khi vượt ngưỡng - Mọi bước đều được ghi vết

2. Bối cảnh: Ada Computer và tiền lệ Em Huyền

Ngày 2026-09-25, Ada (ada.cx) ra mắt Ada Computer: thay vì chỉ trả lời, agent được gắn tool để dùng chính hệ thống của doanh nghiệp hoàn thành việc của khách. Ba loại tool: API tools (nối API có sẵn, agent làm việc từ order / số dư / booking thật), Code tools (luật nghiệp vụ chạy sandbox Python để refund / entitlement theo policy chứ không theo ý model), MCP tools (nối MCP server có sẵn, từng tool mặc định tắt, bật tay). Doanh nghiệp quyết khi nào tool chạy và mọi bước được trace trong conversation view.

Ghi chú trung thực: bài gốc trên ada.cx chặn bot (403 ở cả 3 công cụ fetch), nên phần phân tích dựa trên nội dung announcement JOY cung cấp, không phải toàn văn bài viết.

Tiền lệ nội bộ: Em Huyền, agent trên DOSClaw, đã làm đúng pattern này ở quy mô nhỏ - nhận yêu cầu và tự reset thiết bị cho user. Tức là concept đã được chứng minh chạy thật; câu hỏi chỉ là productize nó trong Crove-Desk cho mọi doanh nghiệp dùng.

3. Hiện trạng repo - đã có gì, thiếu gì

Toàn bộ nhận định dưới đây đã kiểm chứng bằng đọc code trực tiếp, ngày 2026-09-26. Mỗi dòng ghi rõ đường dẫn để đối chiếu.

Thành phầnTrạng tháiBằng chứng trong code

Audit từng lần gọi tool Đã có Models AgentRun, AgentStep, AgentToolCall (risk level, preview tham số / kết quả, duration); hiển thị tại dashboard /dashboard/agent-runs.

Policy-as-code (ngưỡng tiền, entitlement quyết định hành động) Thiếu PolicyGuard chỉ có giới hạn tĩnh (số lần gọi, kích thước tham số). Chưa có chỗ viết luật kiểu "refund dưới 500 nghìn thì tự chạy, trên thì cần duyệt".
Staff approval gate (CS lead duyệt khi vượt ngưỡng) Thiếu Cơ chế confirm hiện có chỉ hướng về khách hàng. Không có hàng chờ duyệt cho người vận hành, cũng không có flow "agent tạm dừng, chờ duyệt, chạy tiếp".
Mô hình secret cho tool gọi ra ngoài Một phần MCP server config có Headers (internal/ai/mcps/types.go) nhưng chưa có nguyên tắc "credential không bao giờ vào context của model" áp hệ thống cho business API tool mới.
Phát hiện an toàn kèm theo: MCP tool ghi dữ liệu đang bị mặc định là "read"

Trong internal/ai/tooling/registry.go, hàm Resolve() trả về MCP tool với RiskLevel: "read" và RequireConfirmation: false một cách vô điều kiện - trong khi MCP server có cung cấp sẵn cờ readOnlyHint trên từng tool (internal/ai/mcps/types.go) nhưng code chưa dùng nó. Nghĩa là nếu sau này nối một MCP server có tool ghi (tạo deal, cập nhật subscription), tool đó vẫn được classify là read và đi qua policy như hành động đọc.

Đây không phải lỗ hổng đang khai thác được ngay (chưa có MCP server ghi nào được nối, và allow-list admin vẫn phải bật tool), nhưng là bẫy an toàn sắp sửa nổ khi tính năng này mở rộng. Đề xuất xử lý trong Pha 2: risk level của MCP tool suy từ readOnlyHint + ghi đè tay bởi admin, thay vì mặc định read.

4.1. Tool Registry mở rộng - business API tool là dữ liệu, không phải code

Thêm một giá trị api vào enum ToolSourceType và một bảng mới (đề xuất tên t_action_tool, đăng ký vào AutoMigrate theo quy ước repo) với các trường chính:

  • code, name, description - định danh và mô tả đưa vào system prompt của agent.
  • endpoint: method + base URL + path, kèm JSON schema của tham số đầu vào (schema này vừa để validate tham số model sinh ra, vừa là hợp đồng công khai của tool).
  • auth: tham chiếu secret (tên env var hoặc key trong secret store), không bao giờ lưu giá trị secret trong DB.
  • risk_level (read/write), policy_expr (biểu thức ngưỡng, xem 4.2), enabled (mặc định FALSE - off by default đúng như Ada), dry_run, timeout_ms, rate_limit, idempotency_mode.

Trang quản lý dùng đúng DashboardCrudPage sẵn có của repo (filter / pagination / form / confirm đều miễn phí), không viết trang riêng. Khi resolve tool, Registry.Resolve() mở rộng: tra t_action_tool trước, sau đó mới rơi về các nguồn hiện có.

4.2. Policy Engine v1 - biểu thức CEL thay sandbox Python

Ada dùng Python sandbox cho code tools. Với Crove-Desk, v1 không cần nặng đến thế: một expression engine là đủ cho 90% luật nghiệp vụ (ngưỡng tiền, điều kiện trạng thái, entitlement). Đề xuất CEL (cel-go): pure Go, không Turing-complete (không loop, không IO - không thể lạm dụng), đánh giá tất định, đã chiến đấu trong production ở Google. Model không bao giờ viết policy - model chỉ đề xuất tham số, policy là văn bản do admin soạn sẵn gắn vào từng tool.

Ví dụ policy expression gắn vào tool "refund_order" 
// cho phép tự chạy khi: đơn đã giao + số tiền trong hạn mức
order.status == "delivered" && refund.amount <= 500000
  → verdict: allow

// vượt hạn mức: vẫn hợp lệ nhưng cần người duyệt
order.status == "delivered" && refund.amount > 500000
  → verdict: require_approval

// còn lại: từ chối thẳng
  → verdict: deny

Context đưa vào biểu thức gồm: dữ liệu conversation, hồ sơ customer (từ mirror t_customer đã đồng bộ với CRM), và tham số action model đề xuất. Verdict trả về một trong ba: allow / deny / require_approval, và verdict này được ghi vào bản audit.

Lựa chọn kỹ thuật (CEL so với expr-lang so với goja) để chốt lúc vào Pha 1; tiêu chí là: pure Go, safe by default, có khả năng test expression offline. Nếu sau này xuất hiện use case cần logic phức tạp hơn expression (vòng lặp, gọi nhiều API), khi đó mới đánh giá sandbox tổng quát (WASM hoặc process isolé) - không làm vội.

4.3. Staff Approval Gate - mảnh HITL còn thiếu

Repo đã có interrupt confirm cho khách hàng; gate phía người vận hành tái dùng đúng cơ chế đó nhưng đổi phía duyệt:

  1. Policy trả require_approval → tạo bản ghi t_tool_approval (tool, tham số đã hash, conversation, verdict, hạn chót).
  2. Agent trả lời khách ngay: "yêu cầu của bạn đã được ghi nhận, đang chờ duyệt từ đội hỗ trợ" - khách không bị treo.
  3. CS lead thấy hàng chờ trong dashboard, bấm Duyệt hoặc Từ chối (kèm ghi chú).
  4. Duyệt xong, executor chạy tiếp và kết quả đẩy ngược vào conversation; từ chối thì agent thông báo lịch sự cho khách.

Ưu tiên thiết kế này vì nó tái dùng interrupt infrastructure hiện có, và quan trọng hơn: quyết định rủi ro tài chính nằm ở con người, không nằm ở prompt.

4.4. Executor và nguyên tắc credential

  • HTTP client dùng chung với timeout, retry có ý thức về idempotency (chỉ retry method an toàn hoặc khi có idempotency key).
  • Secret resolve tại thời điểm gọi từ env var / secret store; giá trị secret không bao giờ được đưa vào context model, không vào log, không vào preview tham số trong audit.
  • Kết quả tool cắt gọn (size limit) trước khi trả về model để tránh phình context.

4.5. Trace và audit

Bảng AgentToolCall đã ghi risk level, tham số, kết quả, duration - mở rộng thêm: verdict của policy, ID approval (nếu có), và cờ dry-run. Hiển thị tại /dashboard/agent-runs vốn đã có. Việc render từng bước tool ngay trong conversation view (dạng card gập lại được) là nâng cấp UI theo sau, không phải điều kiện để chạy tính năng.

6. Guardrails - điều kiện bắt buộc trước khi bật

Đây là phần khó nhất của tính năng, và là phần announcement của Ada không nói kỹ. Bảy nguyên tắc, tất cả là điều kiện hoàn thành của Pha 2 - action ghi không bật nếu thiếu bất kỳ mục nào:

  1. Off by default từng tool. Bật một tool là một hành động có chủ đích của admin, có confirm ghi rõ hậu quả.
  2. Least privilege. Mỗi tool một credential riêng, giới hạn đúng method/path cho phép; credential không bao giờ vào model context.
  3. Ngưỡng + approval. Mọi action ghi có ngưỡng; vượt ngưỡng thì dừng chờ người duyệt. Mặc định an toàn: tuần đầu mọi action ghi cần duyệt, sau đó mới nới theo số tiền.
  4. Idempotency. Idempotency key theo bộ (conversation, tool, hash tham số) với TTL - retry không bao giờ hoàn tiền 2 lần.
  5. Rate limit. Theo tool và theo conversation (tái dùng pattern rate limit đã làm cho public endpoint ở commit 61832f4c).
  6. Audit bất biến. Mỗi lần gọi ghi đủ: tham số, policy verdict, approval, kết quả, lỗi. Không có nút xóa audit.
  7. Kill switch. Một công tắc global + một per agent để tắt toàn bộ action tools ngay lập tức, không cần deploy lại.

Bổ sung hai chế độ vận hành: dry-run (tool mới chạy đủ policy + audit nhưng không gọi ra ngoài thật) và verify khách hàng trước action nhạy cảm (câu hỏi xác minh dựa lịch sử; OTP là open question, xem mục 8).

7. Lộ trình và ước lượng effort

PhaEffortNội dung và tiêu chí xong
Pha 0 - Spike 1-2 ngày Một tool read-only chạy end-to-end trong 1 luồng thật: đăng ký tool trong DB → agent loop expose → gọi được → audit hiện trong agent-runs. Không có policy, không có approval. Mục tiêu duy nhất: chứng minh vòng đời và ra quyết định go/no-go với chi phí thấp nhất.
Pha 1 - Registry + Policy 3-5 ngày Bảng t_action_tool + dashboard CRUD + executor an toàn + CEL policy engine + dry-run + i18n đủ zh-CN / en-US (theo quy ước repo). Xong khi: tạo tool qua dashboard, gắn policy, agent gọi được với verdict ghi audit.
Pha 2 - Approval + an toàn ghi 3-5 ngày Staff approval gate + idempotency key + rate limit + kill switch + sửa risk level MCP tool (phát hiện mục 3). Xong khi: 1 action ghi thật chạy trọn vòng "policy → chờ duyệt → duyệt → thực thi → trace".
Pha 3 - Hoàn thiện (tùy chọn) 2-4 ngày Render tool step trong conversation view, thư viện policy mẫu (refund / entitlement / reset), nối MCP server nội bộ của ecosystem Crove. Ước lượng lại khi chạy.

Ước lượng thô cho solo dev có agent hỗ trợ, dựa trên việc khung governance đã có sẵn. Tính lại tại từng pha - đặc biệt Pha 1 vì đụng schema mới + dashboard + i18n.

8. Rủi ro và câu hỏi mở

  • Model chọn sai tool hoặc sai tham số. Giảm thiểu: JSON schema validate cứng trước khi chạy, policy chặn lớp 2, và bắt agent xác nhận với khách khi yêu cầu mơ hồ. Chấp nhận còn sót rủi ro - vì lý do đó mà ngưỡng approval mặc định bảo thủ.
  • Khách giả danh để kích hoạt action. Action nhạy cảm cần verify danh tính trước. Câu hỏi mở: câu hỏi xác minh dựa lịch sử mua đủ chưa, hay cần OTP? Quyết định khi có use case thật.
  • Chi phí và độ trễ. Mỗi tool call thêm 1 round vào reply loop. Giới hạn bằng MaxCallsPerRun đã có sẵn trong PolicyGuard, và chỉ expose tool liên quan từng agent.
  • Ai viết policy? JOY solo - expression thuần là rào cản. Thiết kế dashboard cần form ngưỡng đơn giản cho case phổ biến (số tiền + điều kiện rơi vào dropdown), expression chỉ cho case nâng cao.
  • Có nên vẽ luồng action bằng flowgram không? Backlog đã có mục "Visual AI Workflow Canvas" đang Under Consideration. Không gộp vào đề xuất này - để sau khi 2 pha đầu chứng minh giá trị.

9. Khuyến nghị và quyết định cần từ JOY

Khuyến nghị: duyệt Pha 0 ngay (1-2 ngày, không đụng action ghi, rủi ro thấp) để chứng minh vòng đời end-to-end. Pha 1-2 chỉ khởi động khi có sẵn 2-3 use case thật - đề xuất đầu tiên: tra trạng thái đơn hàng / thiết bị (read-only), hành động thứ hai kiểu Em Huyền (reset thiết bị, có approval gate).

Ba quyết định cần từ JOY:

  1. Duyệt làm Pha 0 không?
  2. Use case thật đầu tiên là gì? (đề xuất: tra trạng thái đơn / thiết bị - read-only, an toàn tuyệt đối)
  3. Chính sách ngưỡng mặc định: mọi action ghi cần duyệt trong giai đoạn đầu, sau đó nới lỏng theo số tiền - đồng ý không?
